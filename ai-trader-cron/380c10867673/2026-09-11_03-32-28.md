# Stock Analysis — Stage 2 Breakout-Pullback + RR Scoring

Technical-analysis-only methodology for US equities. Used by the AI-Trader paper-trading cron as the analytical backend behind `/tmp/ai_trader_scan.py`. No fundamentals, no sentiment, no news — pure price-action + technical indicators via yfinance.

## When to use

- Computing TP1 (+20%) / TP2 (+40%) lines from `avg_cost` (FIFO-recompute authoritative)
- Scanning a stock pool with the Stage 2 breakout-pullback filter
- Computing MA10/MA20 trailing-stop levels and detecting breaches
- Identifying cap violations (any single position > 10% of total MV)
- Scoring a Stage 2 candidate with RR≥0.8 inclusion threshold
- Comparing drift decomposition across consecutive scans (cron cadence)

## Cost reconstruction from scan output (CRITICAL — don't skip)

`/tmp/ai_trader_scan.py` prints `現價` and `PnL%` but does NOT print `avg_cost`. To compute TP1/TP2 lines, you need cost. **Two reconstruction methods**, pick based on what you have:

### Method 1: from scan's `PnL%` and `現價` (most common)

```python
# scan line:  HOOD qty=74.0 現價=$114.44 ...PnL% = 19.6
cost = cur_price / (1 + pnl_pct / 100)
# = 114.44 / 1.196 = $95.71
```

This is the **only** way to derive `avg_cost` from the scan's stdout — the script intentionally hides cost for "FIFO recompute owns that" semantics.

### Method 2: read `/tmp/ai_trader_tp1_state.json` for state-recorded lots

The state file's per-symbol blocks (`HOOD.entry_price`, etc.) record historical cost for closed lots. For OPEN lots, the cost is implicit in the FIFO recompute's positions table — but that table is NOT in any /tmp file, so Method 1 is the only option for live positions.

### Method 3 (best, when available): the actual `avg_cost` column in the trades_log

`/tmp/ai_trader_trades_log.json` has `action: "buy"` entries with `price` field — for a single-lot position, that buy price IS the avg_cost. For multi-lot positions, FIFO recompute maintains the running avg (out of cron scope).

## TP1 / TP2 line arithmetic

```python
tp1_line = avg_cost * 1.20   # +20% above cost
tp2_line = avg_cost * 1.40   # +40% above cost
pnl_pct  = (cur - avg_cost) / avg_cost * 100   # the scan prints this

# TP2 gap (price-space, NOT pct-space) — always report this way
tp2_gap_pct = (tp2_line - cur) / cur * 100
# positive → TP2 line is above current price (needs upside to fire)
# negative → already past TP2 (would have fired)
```

**Why price-space, not pct-space**: `(tp2 − now)/now` ≠ `(40 − pnl_pct)` — denominators differ. Real case (cron #25, SNDK entry $1372.20, now $1757.57, pnl_pct = +28.1%):
- pct-space gap: `40 − 28.1 = 11.9%` ❌ (computes "additional PnL needed" relative to entry)
- price-space gap: `(1921.08 − 1757.57) / 1757.57 × 100 = 9.30%` ✅ (price distance)

Always compute from prices, never from PnL%. See `ai-trader-cron` skill pitfall "TP2 gap arithmetic".

## MA10/MA20 trail stop — two anchor conventions

The scan reports `止蝕=$X.XX` for each position. This is **one of** two things, depending on whether the position has crossed TP1:

| Phase | Active SL formula | Why |
|-------|-------------------|-----|
| Pre-TP1 (PnL < +20%) | `avg_cost × 0.95` | Fixed entry-anchored 5% stop |
| Post-TP1 (PnL ≥ +20%) | `max(MA10[t], MA20[t])` (or whichever is higher) | Trail-following dynamic stop |

**Diagnostic check**: if `止蝕 ≈ cur_price × 0.95` (within 1%), the SL is a **live MA10-style trailing stop** that follows price, NOT entry-anchored. Real case (cron #30, HOOD cost $95.71):
- Entry-anchored 5% would give: `$95.71 × 0.95 = $90.92`
- Scan reports: `$108.72`
- Sanity check: `$108.72 / 0.95 = $114.44` = current price → **scan uses `cur × 0.95`**

This means HOOD's SL is **active and dynamic**, not entry-anchored. As price moves up, SL moves up with it.

**Pitfall**: when computing the 5% SL buffer, **always use the scan-reported `止蝕` value**, not `avg_cost × 0.95`. The two diverge sharply for post-TP1 positions.

## RR scoring (RR = Reward/Risk ratio)

After a Stage 2 candidate is identified, score it as:

```
RR = (tp2_line - cur) / (cur - stop_line)
```

Where:
- `tp2_line = avg_cost × 1.40` (or use a different target if scoring a fresh entry)
- `cur = current price`
- `stop_line = active SL` (MA10/MA20 if post-TP1, else `avg_cost × 0.95`)

**Inclusion threshold**: RR ≥ 0.8 (configurable). Below that → reject even if Stage 2 passes.

For a fresh entry, the typical scoring is:
```
entry_proposed = current_price   # or breakout level
target        = entry_proposed × 1.20   # TP1
stop          = entry_proposed × 0.95   # 5% fixed
RR            = (target - entry_proposed) / (entry_proposed - stop)
             = 0.20 × entry_proposed / 0.05 × entry_proposed
             = 4.0  ← fixed RR for any new entry at 5%/20% TP1 setup
```

So RR ≥ 0.8 is essentially always satisfied for fresh entries — it's a sanity floor, not a real filter. The real scoring happens at Stage 2 (price action + structure).

## Pitfalls

### Don't compute TP1/TP2 from `cost = cur × (1 - pnl_pct/100)` (sign-flip bug)

The correct formula is `cost = cur / (1 + pnl_pct/100)` because `pnl_pct = (cur - cost)/cost`. If you accidentally use `(1 - pnl_pct/100)`, you'll get cost > cur when pnl_pct > 0, which then flips TP1/TP2 to below current — visually equivalent to "TP1 already triggered" when it isn't.

```python
# WRONG:
cost = cur * (1 - pnl_pct / 100)   # 100 * 0.804 = 80.4 (but pnl is +19.6%, so cost should be 83.6)

# RIGHT:
cost = cur / (1 + pnl_pct / 100)   # 100 / 1.196 = 83.6 ✓
```

### 止蝕 ≠ avg_cost × 0.95 once a position crosses TP1

The scan prints 止蝕 dynamically. Pre-TP1, it's `cost × 0.95`. Post-TP1, it's MA10/MA20 trail. If you assume `止蝕 = cost × 0.95` for a post-TP1 position, you'll mis-compute the buffer by 10-20% (e.g. HOOD entry $95.71, but reported SL $108.72 — buffer would be off by $17.80 if you use the wrong formula).

Diagnostic rule: if `(scan_SL / cur_price) ≈ 0.95`, it's a trail stop. If `(scan_SL / cost) ≈ 0.95`, it's entry-anchored.

### Stage 2 loop is structural, not transient

When `Stage 2 候選: 0` repeats 30+ times consecutively, it's a pool-wide condition:
- bb_lo > price across the pool (broad market not yet in pullback zone)
- 32-position saturation blocks new entries
- Cash floor hard block ($207 < $100 floor check, or close to it)

Treat consecutive zero counts as a **P-MR-294 pattern**, not a per-cron miss. The skill's pool-loop counter is the canonical record.

### RR for fixed TP1/SL setup is constant = 4.0

For any fresh entry with `target = entry × 1.20, stop = entry × 0.95`, RR = `(0.20 × entry) / (0.05 × entry) = 4.0`. The "RR ≥ 0.8" inclusion threshold is a sanity floor — always satisfied. Don't be surprised when "Stage 2 + RR scoring" never surfaces an RR rejection; the real filter is Stage 2, not RR.

### Cap-violation drift attribution is qty × Δprice, NOT Δprice alone

When DE drifts -$14.28 across 2h, the contribution is `17 × -$0.84 = -$14.28` — not just `-$0.84`. Always multiply by qty before ranking. Same for RKLB: `126 × -$0.64 = -$80.64`, which dominates despite the small per-share delta.

### Drift decomposition ranks by absolute $-amount, not by %change

A stock with -2% move on $50,000 MV is a -$1,000 contributor (large absolute). A stock with -5% move on $5,000 MV is a -$250 contributor (smaller absolute). The cron template sorts by dollar amount, not by PnL%.
