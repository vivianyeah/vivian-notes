### ⚠️ One anomaly found: the 14-day retention prune is dead code

The repo holds **726** cron files spanning **104 distinct days** (2026-07-28 → 2026-11-12), and the source directory has 1,412 files going back to 2026-05-04. The 14-day window only yields 97 files.

**Root cause — ordering bug in the script.** Line 103 prunes, line 108 redacts:
```bash
find "$CRON_TARGET" -name "*.md" -mtime +14 -delete    # line 103 — prune
find "$CRON_TARGET" -name "*.md" -exec sed -i -E 's|ghp_...|...|g' {} \;   # line 108 — redact
```
`sed -i` rewrites every file in the tree and **re-stamps its mtime to now**. After one run, all 726 files carry mtime = run time, so the next run's `-mtime +14` matches **0 files** (confirmed: 726/726 repo files have mtime 2026-11-12 04:30; prune matched 0). The prune only ever worked in commit `5ce314d` (2026-09-04) before the redaction step was introduced.

Net effect: `ai-trader-cron/` is **39 MB** working tree / **30 MB** `.git` and grows ~1–2 MB/day indefinitely, instead of holding a rolling 14 days.

**I did not change it** — pruning600+ files is a retention-policy decision that could surprise you, and this run was scoped to backup + report.
