## One anomaly I chased down (not a failure)

The script emitted `WARN: git pull failed (likely dead token)` — yet the push succeeded ~20s later. That looked contradictory, so I reproduced it in isolated sandboxes instead of assuming:

1. The global store helper returns the **first** host+username match. A **complete but invalid** entry sitting first *shadows* a valid one behind it (verified: `[invalid, live]` → 401; `[live, invalid]` → success). A *user-only* entry doesn't shadow.
2. On 401 git calls the helper's `reject` action, and the store helper **erases** the rejected entry (verified).
3. Hence: first op fails → git erases the stale entry → every subsequent op succeeds. **Self-healing.**

The `WARN` line is expected on such a tick. P1 (PAT 200) is the authority on liveness — the PAT is fine, and no rotation is needed.

Two knock-on facts worth flagging:
- `/tmp/.git-credentials` is now **2 entries, not 3** — git's own `reject` erased the `x-access-token` duplicate of the live PAT during the tick. Fewer on-disk copies of a live PAT is an improvement; don't recreate it.
- The store is **shared** by pipelines A and B, so entry count isn't stable — count it, don't assume it. Pipeline B's `ls-remote` still resolves fine.
